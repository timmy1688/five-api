# Five API 开发计划

目标是交付一套可商用的轻量多租户 AI 网关：平台负责开户与额度，租户管理自己的 API Key，已有代理接口可靠转发并按租户计费。参考 LiteLLM 的租户边界、Key、预算与故障转移，按当前业务范围选择能力。

- 更新日期：2026-10-25。
- 代码基线：`dd94680`。
- 当前状态：M1–M4 已实现并完成本地验收；远端 CI 由提交触发。
- 开发条件：本地 Uvicorn --reload（5002）与 Vite（5001），MySQL、Redis 沿用现有容器作为依赖；网关容器已停止。当前测试数据可清理，无需额外备份。发布阶段再验收单镜像 Compose，不建设多副本或第二套环境。
- 当前交付：0.4.0 开发版，迁移 18–22；验收记录见文末。
- 权限依据：[多租户权限设计](PERMISSIONS_DESIGN.md)。

原计划的 34 项任务收敛为下面 17 项，任务编号按四个交付批次重排。按依赖推进，并同步记录实际验收结果。管理 API 复用短期 JWT，不新增长期管理凭证系统。

## 已确定的产品范围

1. 只有平台管理员和租户账号两种固定角色，先按一个租户一个登录账号实现。
2. 平台创建账号、配置模型与额度、管理渠道和统一报价，并可停用租户。
3. 租户可改自己的密码，管理自己的 Key，查看对应的用量、费用与必要请求元数据；不能创建账号、管理角色或提高租户总额度。
4. 客户开通、额度调整和结算采用人工与线下流程，不接入在线支付。
5. 保留已有 OpenAI、Anthropic 及现有多模态接口的兼容性；所有仍可调用的接口、后台任务和历史查询必须执行租户范围检查。

MVP 进一步限定：角色与账号租户绑定创建后不可改；客户业务只有一个租户启停入口；租户界面以一个 Key 管理页和改密入口为主。暂不提供租户删除、合并、转移、自助导出、公开找回密码或专用 Key 原地轮换接口。Key 更换通过新建、替换应用配置、撤销旧 Key 完成。已有高级 Key 限制默认继承或收起，不新增策略配置页面。

商业计价采用模型售价 × 渠道价格倍率，渠道可为单个模型设固定价；租户可在 Key 上选择渠道，按实际服务渠道计费。Key 限额和租户总限额同时生效。客户只看到渠道名称、倍率、模型、价格和健康状态，不读取上游地址与密钥。不记录上游成本与毛利；按租户定制合同价、分时售卖价和复杂套餐不列入本计划。

新租户默认累计额度为 0、不开启自动月重置；平台手工调整总上限并保留已用历史。多个 Key 共享租户总额度，Key 自身上限不构成独立余额。额度与两类 Key 的安全要求见[多租户权限设计](PERMISSIONS_DESIGN.md)，复用下面已有任务落实，不增加新的系统或交付批次。

## 对照 LiteLLM 后的取舍

这些取舍依据 Five API 的产品范围，不以 LiteLLM 是否具备某项能力作为唯一标准。

| 能力 | LiteLLM 的参照点 | 本计划决定 |
| --- | --- | --- |
| 租户、Key、模型授权和预算 | 共享网关按归属隔离访问与费用 | 必做，采用 Tenant 与 Key 两层约束 |
| 角色与用户管理 | 区分平台和受限用户，并提供组织、团队角色 | 保留两种固定角色；移除动态角色表、权限数组、角色 CRUD 和编辑页面 |
| 组织、团队、成员层级 | 支持多层资源及费用归属 | 复用现有 Team 预算逻辑演进为 Tenant，不保留 Tenant 加 Team 的双层客户组织 |
| 故障转移、限流与成本记录 | 网关基础能力 | 保留并验证已有实现，修复计费和协议边界 |
| SSO、SCIM、委派管理、云密钥管理 | 企业身份与治理能力 | 从本计划删除，当前人工开户不需要 |
| OpenTelemetry 与外部观测平台 | 标准追踪与集成 | 从本期删除；使用请求 ID、结构化日志和现有 Prometheus |
| Helm、Terraform、多副本与组件拆分 | 多种生产部署路径 | 从本期删除；完成单机 Compose 的升级、恢复和退出验证 |
| 插件框架、配置导入导出、新增原生厂商适配 | 扩展与生态建设 | 从本计划删除；继续支持已有兼容上游 |
| 管理操作审计 | 追踪配置与权限变化 | 保留最小记录，覆盖开户、额度、价格、渠道和 Key 操作，不建设审计平台 |
| 正文审计、AI 审查、复杂成本分析 | 更广的治理与运营能力 | 不新增、不扩建，租户控制台聚焦 Key、用量与费用 |

参考：[LiteLLM 多租户架构](https://docs.litellm.ai/docs/proxy/multi_tenant_architecture)、[RBAC](https://docs.litellm.ai/docs/proxy/access_control)、[故障转移](https://docs.litellm.ai/docs/proxy/reliability)、[企业能力](https://docs.litellm.ai/docs/enterprise)、[OpenTelemetry](https://docs.litellm.ai/docs/observability/opentelemetry_integration)、[生产部署](https://docs.litellm.ai/docs/proxy/deploy)。

已有的粘性会话、缓存计量、滚动限额、基础告警与多模态接口保持兼容，不重复建设。已有洞察、审计等非核心页面仅在平台侧按需保留，CSV 账单对账按本轮要求删除，不向租户默认开放；其存量接口同样纳入授权清理。精简计划不等于立即删除业务数据或已有接口，实际清理在迁移与回归完成后执行。

## M1 简化权限与多租户

- [x] **M1.1 租户模型与历史归属。** 优先复用现有 Team 的额度、状态和统计逻辑演进为 Tenant；业务概念只有一个客户层级。固定角色与 tenant_id 绑定创建后不可修改，租户账号使用唯一归属约束；Tenant 是客户业务启停的统一来源。日志、汇总和已有任务保存归属，结算账本在 M2.3 新增时绑定 tenant_id；核对旧 Team、未分组 Key、账号和历史数据的迁移映射。
- [x] **M1.2 移除动态 RBAC。** User 使用 `platform_admin`、`tenant` 两种固定角色。复用密码、JWT、令牌撤销和默认密码保护；管理 API 采用账号密码登录后使用 Bearer JWT，默认 60 分钟，aud 固定为 five-api-management，不接受推理 Key 或逐次 Basic Auth；替换 `require_permission()`、`ALL_PERMISSIONS`、动态权限数组与角色初始化，移除角色接口、前端角色页面和权限勾选。旧 Role 仅用于一次迁移映射，移除运行依赖；物理清理旧表可在备份恢复验证后收尾，不建设长期兼容层。
- [x] **M1.3 统一租户范围与可写字段。** 后台账号与推理 Key 分别确定租户，平台操作使用明确的管理员入口。所有开放的列表、详情、统计、批量和既有任务使用同一租户边界；拒绝伪造或缺失归属。租户 Key 接口采用独立的字段允许清单，拒绝附带的角色、tenant_id、已用金额、计价和周期策略；不复用管理员全字段更新模型。
- [x] **M1.4 开户与最小租户控制台。** 平台开通、调整额度、启停和人工重置密码，记录关键变更；临时密码首次登录须修改。租户只有 Key 管理页和改密入口，页面展示总额度、已用、可用及 Key 详情，占用金额用于详情排查。Key 仅一次展示、响应不缓存、前端不保存明文；支持创建、限制、停用和撤销，手工更换新旧 Key 不恢复租户额度；高级限制默认继承或收起。

### 验收标准

1. 平台能开通两个租户；两者都能管理自己的 Key，不能访问对方的任何业务资源。
2. 租户直接调用账号创建、角色修改、平台配置或跨租户接口仍被拒绝，不能通过请求体改变身份。
3. 动态权限数组、角色编辑页与旧角色授权执行路径完成移除；固定角色和服务端租户查询承担授权，旧 Role 表不再参与运行。
4. 迁移后保留原 Key 与历史费用的可解释归属；旧自定义角色不能自动提升为平台管理员。
5. 停用租户阻止其后续后台业务与推理请求；修改登录密码撤销旧登录令牌，不意外撤销应用 Key。保护最后一个有效平台管理员。
6. 租户总额度只有平台可调，多把 Key 不增加总上限；查询 API 不返回既有 Key 明文，撤销阻止旧 Key 的新调用，手工更换不减少租户已用与历史费用。
7. 租户请求不能修改账号归属、角色、已用、报价或周期；租户没有自助导出、租户删除或转移入口，账号业务启停只有一个来源。

M1 的管理接口、凭证选择依据与接入示例见 [Key 管理 API](MANAGEMENT_API.md)。租户使用 `/api/keys` 创建自己的 Key；平台管理员通过同一入口创建平台自用 Key，自动归内部空间。未提供管理员代租户创建入口，禁止指定客户 tenant_id。旧管理 JWT 因缺少新的 aud 必须重新登录。

## M2 网关与计费可靠性

- [x] **M2.1 请求 ID 与原生错误。** 每次请求生成内部唯一 ID，客户端 ID 单独记录；预算预留与结算只使用内部 ID。统一 OpenAI、Anthropic 的鉴权、限流、参数校验和流式错误，保留合适的上游错误及退避响应头。
- [x] **M2.2 用量与报价快照。** 沿用输入、缓存读、缓存写、输出及已有按次计价，统一协议用量口径；区分上游、估算和混合计量。保存实际报价与费用明细，分别记录平台成本和客户计费，首期采用统一模型报价。
- [x] **M2.3 事务与幂等结算。** 用一份 MySQL 持久化结算记录保存待处理用量，以内部 ID 保证幂等；Key、租户扣费、请求日志和每日汇总在同一事务内提交。使用现有数据库与进程内恢复循环，不新增消息队列或通用事件平台。
- [x] **M2.4 结算恢复与总限额。** 失败结算有限退避重试，重启后恢复；每个请求的预留与待结算占用只计算一次。Key 与租户都需足额预留估算费用，可用不足时不调用上游；无法验证凭证与额度时不默认放行。恢复不重复记账，多把 Key 不绕过租户总额和速率；估算偏差与在途费用如实记录，不承诺绝对零超额。
- [x] **M2.5 必要日志与监控。** 保留请求元数据、简要重试原因、用量费用、关键管理操作和结算失败记录；复用现有 Prometheus 与告警。Authorization、x-api-key、明文 Key 响应和已知上游凭据不进入日志、告警或审计，上游错误入库与返回前脱敏；客户只见自己的使用数据。

### 验收标准

1. 相同客户端 ID 的并发请求分别占用预留，能按内部 ID 查到租户、结果与费用。
2. 模拟租户扣费、日志或汇总写入失败时，没有部分提交；重复恢复不重复扣费。
3. 多把 Key 仍受租户总额度与速率约束，定价和结算失败不静默按零费用处理。
4. 厂商返回用量和估算用量可以区分；报价调整不会改写历史费用。
5. 已有流式、工具调用、号池、故障转移、缓存与多模态接口保持兼容，日志不泄露其他客户信息。
6. 新建或更换 Key、修改上限、重复提交额度调整不能抹掉历史费用；新租户默认累计、不自动重置，存量周期配置按明确映射迁移。

持久化结算记录的幂等不代表上游调用恰好执行一次。上游已计费但进程尚未保存用量的故障窗口需要明确记录，并提供线下对账的处理依据。

## M3 测试与单机交付

- [x] **M3.1 真实 MySQL 与 Redis 测试。** 保留快速单元测试，使用专用测试数据库、Redis 命名空间和可控上游验证事务、唯一约束、Lua、TTL 与结算恢复；CI 自动执行。
- [x] **M3.2 HTTP 流式与客户端兼容。** 通过真实网络连接测试首包前切换、首包后断流、客户端取消、超时及最小 SDK 契约。OpenAI、Anthropic SDK 契约通过真实网络验收；Claude Code、Codex、Cursor 的 CLI/桌面端本次未认证，矩阵中明确列出。实际厂商测试单独运行。
- [x] **M3.3 双租户与 Key 安全矩阵。** 覆盖 Key 生命周期、账号创建拒绝、平台入口拒绝、请求附加敏感字段、筛选与批量、已有下载任务、相同任务 ID、租户停用、历史账单及缓存隔离。验证鉴权与额度异常不放行、手工更换 Key 不减少租户用量、限流有效，以及响应、日志、错误和告警不泄露已知凭据。
- [x] **M3.4 单机恢复。** 沿用单镜像 Compose；验证受信代理 IP、迁移、探针超时、优雅退出及备份恢复。上游加密主密钥外置且不回写数据库，与 JWT 签名密钥用途分离，记录旧同库密钥的迁移和人工维护；不引入云密钥管理或自动轮换服务。
- [x] **M3.5 可重复构建与更新。** 锁定后端依赖，验证前端构建和非 root 镜像，接入基础依赖检查，复用现有 CI 和多架构镜像发布。更新当前环境后执行平台登录、租户登录、建 Key、推理、预算拒绝和费用核对。

### 验收标准

- 全新数据可从迁移启动，当前数据可升级并在隔离库恢复，渠道 Key 可解密且历史费用可查询。
- 真实服务、后端回归与前端构建通过；断流、退出及失败恢复不会留下无法解释的预留或账目。
- 两个租户的数据与状态检查通过，测试清理只处理本次创建的资源。
- 更新与恢复步骤可重复执行；数据库不兼容时按已验证的恢复流程处理，不能只回退镜像。
- 不要求为当前单机交付额外建设多副本、分布式调度、Kubernetes 或第二套部署环境。
- 数据库单独备份不包含可用于解密上游 Key 的主密钥，主密钥单独保管，恢复与配置错误场景已验证。

## 单环境实施与记录

当前开发流程：实现及对应测试 → 本地热更新验证 → 双租户 HTTP/浏览器冒烟与费用核对 → 更新计划和 CHANGELOG。按用户授权直接执行开发环境操作、迁移和必要清理，不额外备份测试数据，不在日常开发中重建或启动网关容器。后续商用发布的备份、HTTPS 与恢复要求仍由 M3 验收。

### 本轮范围补充

- 账号菜单合并为租户账号、平台管理员；保留管理员平台自用 Key，与客户 Key 分开，不代客户创建。
- 租户共享 RPM/TPM/并发，默认 120 / 100,000 / 10，存量迁移显式 -1 保持原吞吐。
- 模型广场按渠道展示客户实际计费价（售价 × 渠道倍率或渠道固定价），导入价格仅补缺失项。
- Key 可选择渠道：不选为全部渠道；选一个即固定价格，该渠道不可用时报错；选多个只在其间故障切换，按实际服务渠道计费。预占按候选渠道中最贵的报价。
- 可用性默认每 15 分钟；GPT/Claude 降智参考默认 24 小时，支持手动、定时和持久化历史，最多两个并发；当前实际 DeepSeek 的 6 个入口已完成首轮自动健康检测。
- 删除 CSV 账单对账。后台保留结算重试，独立恢复页签移除，仅在确有异常时提示。
- 系统设置分为网关配置、路由策略、告警通知、监控接入，按组保存，高级规则折叠。
- 依赖使用国内镜像下载。项目不提供 HTTPS 与反向代理配置，由部署方自行处理。
- 网关容器无状态，不挂载持久卷；加密主密钥与 JWT 签名密钥可选，在 Compose 中配置，未配置时用内置加密密钥与每次启动随机的 JWT 密钥。
