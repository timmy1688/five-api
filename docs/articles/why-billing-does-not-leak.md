# 为什么我们的计费不会漏钱：一个 AI 转售网关的记账设计

> 适合发布到 V2EX、LINUX DO 等社区。项目地址：https://github.com/timmy1688/five-api（MIT）

做 AI 接口转售的朋友应该都遇到过这几种事：

- 客户余额只剩 1 美元，同时开 50 个并发，每个请求都通过了余额检查，最后欠了 20 美元。
- 新上了一个模型忘了配价格，跑了一周才发现全按 0 记账。
- 网关进程重启，正在跑的长请求上游已经扣了钱，网关这边一笔都没记。
- 客户端断流，网关以为请求失败没扣费，但上游已经生成了几千 token。

这些都不是性能问题，而是记账设计的问题。我们做 [Five API](https://github.com/timmy1688/five-api) 时给自己定了一条规矩：**先把钱占住，再放请求出去；账和日志要么一起写进去，要么都不写。** 下面讲具体怎么做的，以及它的代价。

## 一、先足额预占，再调上游

很多网关的做法是「先放行，返回后再扣费」，或者只预扣输入部分。问题在于并发：50 个请求同时读到余额 1 美元，都认为够用。

我们的流程是：

1. 估算这次请求最多花多少钱：输入 token 按上限估（中日韩字符按 1 字 1 token，其他文本按 4 字符 1 token，工具定义也算进去），输出按请求的 `max_tokens`，没填就按 4096。
2. 在 MySQL 事务里按固定顺序锁住租户行、Key 行，把「已用 + 所有在途请求的预占 + 这次预占」和额度比较，够了才写一条预占记录。
3. 预占记录写成功、标记为「已发出」之后，才真正请求上游。

因为检查和占用在同一个行锁事务里完成，50 个并发请求是排队过这道门的，第 2 个请求看得到第 1 个的预占。多进程部署时也一样，锁在数据库里，不在进程内存里。

如果数据库或 Redis 出问题、预占写不进去，请求直接返回 503，**上游不会被调用**。宁可拒绝，也不先放行后补账。

## 二、没配价格不放行

模型没配售价时，请求在调上游之前就被拒绝；价格停用的模型也一样。只有显式填 0 才免费。「缺失」和「0」在代码里是两种东西，不会因为字段为空就当作 0 处理。

售价在发请求前就记进预占记录，请求中途管理员调价，这一笔仍按发出时的价格结算。

## 三、扣费、日志同一个事务

上游返回后，先把用量持久化（状态 `pending`），然后在一个事务里同时写：Key 已用、租户已用、请求日志、日用量汇总，并把预占记录改为 `settled`。四个要么都成功，要么都回滚。

如果这个事务失败（比如数据库瞬断），后台任务会重试结算，并保证只结算一次——用请求的内部 UUID 做幂等，重试不会重复扣费。多次失败后标记为 `failed`，在管理后台显示处理入口。

这里有一个刻意的选择：**结算失败绝不重放上游请求。** 上游已经执行过的调用，网关不会因为自己记账失败就再调一次。

## 四、结果不确定的请求，继续占着钱

最麻烦的是「不知道上游有没有执行」的情况：请求已发出，进程被 kill 了；或者上游超时，不知道对方有没有扣费。

我们的处理是把它标记为 `uncertain`，**预占的钱继续占着**，不自动释放，等人工核对。每个进程在 Redis 里有心跳，进程消失后，其他进程会接管它留下的记录：还没发出的直接释放，已经发出的转成 `uncertain`。

这样做的代价是客户可能暂时少一点可用额度，但不会出现「上游扣了钱、网关没记、额度还被放回去」的情况。

## 五、断流也计费

客户端中途断开时，网关按已经转发给客户端的内容计费；上游没有返回用量字段时，按转发的内容估算，并在日志里标明 `usage_source`（上游 / 估算 / 混合），方便对账时区分。上游明确返回 0 用量和缺失用量分开处理，不会把显式的 0 替换成估算值。

## 诚实的边界

- 预占是按估算上限，实际用量超出估算时照实扣费，不会少收，所以余额可能出现一次请求范围内的小额负数。最常见的是没设 `max_tokens` 却输出超过 4096 token。要把上限卡死，让客户端设置 `max_tokens`。
- 计费以上游返回的用量为准，和厂商账单的口径可能不同，上游账户本身也要设预算告警。
- 单个租户的所有请求都要过同一行锁，所以单租户吞吐有上限：8 核机器上模拟测试约每分钟 9000 次，多个租户合计约 2.6 万次。我们认为对转售场景，账准比单租户极限吞吐重要。

## 和 new-api 的差别

new-api 是很成熟的项目，自助注册、在线充值、兑换码这些公开中转站需要的功能做得比我们全。在计费上，按它公开的文档和代码，它只预扣估算的输入部分，余额超过 `trust_quota_usd`（默认 10 美元）时跳过预扣；我们是输入加输出上限足额预占。模型未配置价格时，它返回价格错误，我们直接拒绝请求，两者都不会按 0 白跑。

如果你做的是公开中转站，需要用户自己注册充值，new-api 更合适；如果你是给固定客户开户、按客户精确分账，可以试试 Five API。

## 怎么验证

每一条保证都有对应的自动化测试，CI 每次提交都会跑：

```bash
git clone https://github.com/timmy1688/five-api && cd five-api
./service.sh install
cd backend && ../.venv/bin/pytest -q tests/test_billing_invariants.py tests/test_billing_reliability.py
```

快测里包括：随机生成 3000 组用量验证预占覆盖每一笔扣费、缺价不放行、价格锁定、记账事务失败后恰好恢复一次。连真实 MySQL、Redis 的集成测试（`tests/integration`，用法见贡献指南）还覆盖：两个真实进程同时打同一个租户不超卖；进程被 kill 后已发出的预占转为 `uncertain` 继续占用；客户端断流后不重放上游。

压测脚本会逐笔重算：用日志里的 token 数乘以售价，和实际扣费、Key 已用、租户已用三处对账。真实 DeepSeek 渠道 320 笔流式请求 0 笔不一致，模拟环境 8 轮对账全部通过，原始数据在仓库的 `docs/benchmarks/` 里，命令见 [压测报告](https://github.com/timmy1688/five-api/blob/main/docs/BENCHMARK.md)。

部署只要一条命令：

```bash
./service.sh deploy
```
