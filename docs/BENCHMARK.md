# 压测报告

版本 0.4.0，2026-10-31。压测分两部分：

- **模拟环境**：上游换成本机模拟服务，测网关自身最多能处理多少请求。
- **真实环境**：接真实 DeepSeek 渠道，按正常业务并发，测接入网关后用户能感觉到的差别。

两部分每轮测完都核对计费：每个成功请求只结算一次，每笔费用按 token 数和售价重算一致，Key、租户的扣费合计与日志费用合计一致。所有轮次全部通过。

## 结论

| 问题 | 答案 |
|---|---|
| 一台 8 核机器能处理多少 | 多个租户合计每分钟约 2.6 万次（8 个进程） |
| 单个租户最多多少 | 每分钟约 9000 次，不随进程数增加 |
| 接真实模型后慢多少 | 首字只慢约 6–19 毫秒，感觉不到 |
| 计费会不会出错 | 所有轮次逐笔核对一致，没有多扣、漏扣 |

## 测试环境

- 一台 8 核 16 GB Linux 机器，Python 3.12。网关、MySQL 8、Redis 7 和压测程序都在这台机器上。
- 网关与正式部署相同：`uvicorn --workers N`，镜像默认 N = CPU 核数（最多 8）。
- 压测脚本自己创建临时租户、Key（不限额度和速率），测完删除，不碰已有数据。

## 一、模拟环境：处理上限

上游是本机模拟服务，固定 5 毫秒返回；非流式请求，同时 64 个请求，每轮 4000 次（先预热 300 次）。直连模拟服务每分钟约 39 万次，远高于网关，所以测到的就是网关自己的上限。

| 网关进程数 | 16 个租户（次/分钟） | 相对 1 个进程 | 1 个租户（次/分钟） |
|---|---|---|---|
| 1 | 1.06 万 | 1.0 倍 | 7900 |
| 2 | 1.97 万 | 1.9 倍 | 8400 |
| 4 | 1.93 万 | 1.8 倍 | 8700 |
| 8 | 2.56 万 | 2.4 倍 | 9100 |

- **多租户**：进程从 1 个加到 2 个，能力接近翻倍。再往上增长变慢：4 个进程时每个进程的 CPU 只用了约 73%，MySQL 占约 190%，瓶颈在同一台机器上的数据库。4 个进程略低于 2 个属于同机测量波动。MySQL 单独部署时上限会更高。
- **单租户**：同一租户的每次扣费都要锁住这个租户的余额再更新，请求只能排队，所以约每分钟 9000 次封顶，开再多进程也不变。同一租户开多个 Key 也一样。这是保证余额不被扣穿的代价。
- 这里的模拟请求只有几毫秒，真实模型一次要 1 秒以上，网关在等待上游时几乎不占资源，所以真实场景能同时挂住的连接远多于这里的并发数。

## 二、真实环境：DeepSeek

渠道 `deepseek-v4-flash`（最便宜的模型），流式输出，每次回答最多 64 个 token（约 1.2 秒），请求分散在 4 个租户。每一级并发先直连 DeepSeek、再经过网关，各发「并发数 × 4」次，两边条件相同。

| 同时在线请求 | 成功（网关 / 直连） | 首字耗时中位（网关 / 直连） | 整体耗时中位（网关 / 直连） | 每分钟完成（网关 / 直连） |
|---|---|---|---|---|
| 10 | 40/40 / 40/40 | 179 / 162 毫秒 | 1252 / 1168 毫秒 | 377 / 364 |
| 20 | 80/80 / 80/80 | 172 / 153 毫秒 | 1219 / 1101 毫秒 | 821 / 817 |
| 50 | 200/200 / 200/200 | 168 / 162 毫秒 | 1214 / 1208 毫秒 | 2089 / 2231 |

- 全部成功。网关让首字只慢 6–19 毫秒，主要花在鉴权、预扣费和记账上，相比模型本身的耗时可以忽略。
- 计费：320 次调用，输入 12160、输出 20479 个 token，共扣 0.028159 美元；每笔按 DeepSeek 返回的用量和售价重算都一致，Key 和租户扣费相同。
- 官方账号有限流，真实测试只用正常业务量的并发。探索时把并发加到 400 以上，直连 DeepSeek 就开始返回 429（限流），所以容量上限用模拟环境测。

## 注意事项

- **代理**：经过办公网代理访问 DeepSeek 时，并发 400 直连就有 20% 连接失败，瓶颈在代理。真实测试和正式部署都应直连上游。
- **磁盘**：MySQL 默认保留 30 天 binlog，压测中数万次请求就写出了 1GB。磁盘写满时 MySQL、Redis 停止写入，请求和结算会卡住。生产环境要监控磁盘，处理方法见 [运维文档](OPERATIONS.md)。

## 重新测试

只需要 MySQL、Redis 在运行，不使用开发服务的 5002 端口。

```bash
cd backend

# 模拟环境：默认 16 个租户，--tenants 1 测单租户
../.venv/bin/python -m scripts.benchmark --workers 1,2,4,8
../.venv/bin/python -m scripts.benchmark --workers 1,2,4,8 --tenants 1

# 真实环境：会产生少量上游费用；默认并发 10、20、50，4 个租户，最高允许 200
../.venv/bin/python -m scripts.real_benchmark --channel <渠道 ID> --model deepseek-v4-flash
```

加 `--output 文件路径` 可保存 JSON 结果。本次原始数据：[模拟环境](benchmarks/synthetic.json)、[真实环境](benchmarks/real-deepseek.json)。数据来自单机测试，不代表生产容量承诺。
